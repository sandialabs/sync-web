# Repository tools

## `sync-check`

`sync-check` is a thin orchestrator over the repository's existing test commands. It prints a compact status table and stores complete logs plus `summary.json`, `report.md`, and `commands.log` under the ignored `target/sync-check/` directory.

```bash
scripts/sync-check --changed --base origin/main
scripts/sync-check records gateway explorer
scripts/sync-check --full --keep-going
scripts/sync-check --plan --changed
scripts/sync-check --list
```

Changed-file selection includes committed differences from the base, staged changes, unstaged changes, and untracked files. The selected profiles are always printed. Network tests are never started implicitly.

## `sync-network`

`sync-network` provides read-only diagnostics around a network generated by `tests/network/compose/local-compose.sh`. An exact isolated Compose project name is mandatory. Production-like names are rejected.

```bash
scripts/sync-network status --project sync-federation-4
scripts/sync-network wait-ready --project sync-federation-4 --timeout 300
scripts/sync-network probe --project sync-federation-4
scripts/sync-network logs --project sync-federation-4 --tail 50
scripts/sync-network snapshot --project sync-federation-4
```

The initial interface intentionally has no lifecycle or destructive operations. Continue to use the existing harness for creation and teardown. `wait-ready` requires running containers, healthy configured healthchecks, passing router probes, immutable project-scoped topology, fresh social-agent benchmark snapshots, and zero activity/request failures. Snapshots write those semantic checks plus redacted container configuration, bounded logs, HTTP probe results, image/container information, topology, resource statistics, volume sizes, host pressure, Git state, and the shared compact artifact files under `target/sync-network/`. Legacy stacks without project-scoped topology/results are reported as unavailable rather than silently attaching the current global generated files.

## `benchmark-batch-records`

`benchmark-batch-records` runs the deterministic Records scalar-versus-batch matrix without containers through the required verified Wasmer AOT. Each arm uses a fresh scenario, an optimized release binary, fixed counts `1`, `32`, and `1024`, and counterbalanced ordering. The default two-pair run covers staged `get`, committed `resolve`, and proof-bearing `trace`; complete `/usr/bin/time -v` outputs, generated scenarios, hashes, JSON, and a Markdown table are written under ignored `target/batch-records-benchmark/`.

```bash
scripts/benchmark-batch-records --plan
scripts/benchmark-batch-records
scripts/benchmark-batch-records --quick --output /tmp/batch-quick
scripts/benchmark-batch-records --binary journal/target/release/records-test
```

Use identical source, host conditions, counts, and pair order for comparisons. This benchmark isolates deterministic Records/Interface execution; it is not an HTTP, TLS, container, or production-social benchmark.

## Artifact contract

Both tools produce:

- `summary.json` — machine-readable result and Git state;
- `report.md` — concise human-readable disposition;
- `commands.log` — exact commands or diagnostic command summary;
- complete per-check logs or bounded per-container logs where applicable.

Artifacts are local and ignored. They must not be committed. Network configuration and logs are redacted for common secret, token, password, credential, and private-key fields, but operators should still review artifacts before sharing them.
