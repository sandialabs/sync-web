# Sync Web 1.6 resource API transition

Sync Web 1.6 replaces the staged and committed data API. This is a breaking transition with no current aliases, fallback reader, or grant migration.

## Operation and grant matrix

| Previous operation | Current operation | Current grant |
| --- | --- | --- |
| `get`, `get-batch` | blank `use!`, `use-batch!` with `read-only? #t` | `(use! ((read-only? #t)))` for read-only only, or `#f` for both modes |
| `set!`, `set-batch!` | `put!`, `put-batch!` | `(put! BOOLEAN)` |
| `call!` | `run!` | `(run! BOOLEAN)` |
| `resolve`, `resolve-batch` | `retrieve`, `retrieve-batch` | `(retrieve BOOLEAN-OR-RANGE)` |

`copy!` and `copy-batch!` require read-only `use!` authority on every source and `put!` authority on every destination. Conditional put and copy also require read-only `use!` authority on the compared destination.

## Fleet procedure

1. Inventory every staged program, generated request, Gateway caller, browser client, `pi-sync` installation, inbox service, and Source helper that names an old operation or grant field.
2. Pause callers and drain in-flight requests. Do not begin while a write outcome is ambiguous.
3. Take a full pretransition snapshot. This snapshot is the complete rollback boundary; do not attempt a partial code or grant rollback.
4. Snapshot current authorization rules, then clear them or replace them exactly. There is no generalized grant migration and current code does not interpret old grant fields.
5. Install the current code only while the fleet is paused. Persisted old heads, code, history, and transition operations remain interpreted by their persisted old code; do not rewrite them.
6. Reissue least-authority rules using only `put!`, qualified `use!`, `run!`, and `retrieve`.
7. Update staged programs and every inventoried client before resuming traffic.
8. Run correlated canaries: blank read-only inert use, read-only object use with no transition, mutating use with one transition, copy with separate source/destination authority, and historical retrieve with proof verification.
9. Resume callers only after every canary is correlated to its exact request and committed result.

## Owner-gated external consumers

The runtime rollout is separate from this repository change. Inventory and update `pi-sync`, `pi-sync-inbox` and its inbox service, `pi-sync-source`, and `sync-source-flow` only under explicit owner authority. They currently construct or consume operation/grant names and must not be silently activated or mutated from this change.

If any write is accepted but its durable outcome is ambiguous, stop. Do not retry, replace, or infer failure from a missing response. Recover from the full pretransition snapshot only after disposition of the ambiguous operation.
