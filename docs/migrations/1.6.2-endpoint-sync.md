# Sync Web 1.6.2 endpoint synchronization

Version 1.6.2 corrects the existing Interface `update-config!` operation for the exact path `(public interface endpoint)`. The operation now changes both the Ledger public endpoint configuration and persisted Federation endpoint in one local Interface call. It adds no public method, grant, class layout, signing rule, or bridge protocol.

## Upgrade

Use the existing explicit update workflow on a stopped, backed-up copy first. The supported predecessor releases are 1.5.0, 1.6.0 and 1.6.1; unsupported built-in Records generations fail closed. Compose additionally requires the matching predecessor volume marker and `JOURNAL_UPDATE=1`. The deployment marker advances only after Interface installation succeeds. Ordinary 1.6.2 reopen leaves the update flag unset.

This Interface-only patch shares its built-in class generation with 1.6.1. The installer therefore records a private `interface records-version` value to reject reapplication of 1.6.2 instead of mistaking it for its predecessor. This is installer metadata, not a public Journal identity or a user-data field. The Journal SDK crate version does not change.

For a 1.5.0 transition, follow the separate [resource API migration procedure](1.6-resource-api.md), including legacy authorization disposition and client updates. Version 1.6.2 does not translate old grant schemas.

## Repairing an existing mismatch

Installing the patch preserves existing durable configuration; it does **not** automatically align a Federation endpoint that already drifted from the Ledger endpoint.

After upgrading:

1. Preserve the database and configuration preimages, and resolve any ambiguous earlier mutation before continuing.
2. Verify the intended URL against the Journal's signed committed descriptor and its current public configuration. Do not choose a different hostname, key, identity, or relationship merely to repair this mismatch.
3. Through the ordinary local administrator or Root-authorized Interface, issue **one** `update-config!` call at the exact `(public interface endpoint)` path, with the same verified endpoint value. Even when the Ledger configuration already contains that value, this call aligns Federation under 1.6.2.
4. Read back the public configuration. If any endpoint change is still uncommitted, wait for an ordinary signed head containing it before qualifying bridge readiness. A successful configuration call is not itself proof of a new committed head; no-op steps need not append history.
5. Qualify the ordinary bridge/route and use a fresh, separately identified application canary with reciprocal receiver presentation. Retain independent write outcomes and never automatically retry an ambiguous mutation or replay an earlier canary.

The fix retains the signed descriptor checks: if a peer advertises an endpoint that does not match its authenticated signed head, the exchange still rejects. It does not weaken preapproval, key rotation, predecessor continuity, terminal-local authorization, or route selection.

Root-local internal alignment of a current-release database is a separate operator repair, not an automatically executed installer migration. Do not infer such a repair, remote rollout, bridge reset, or rollback from this release. Do not restore a pre-upgrade backup over accepted newer application writes without explicitly disposing of those effects.

## Boundaries

Only the exact endpoint leaf setter is forwarded. Replacing a parent configuration subtree is not a substitute for this operation. The change coordinates two local objects within one Interface call; it does not make multiple nested `run!` operations or cross-Journal workflows atomic.
